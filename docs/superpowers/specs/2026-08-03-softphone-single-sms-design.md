# Одиночное SMS абоненту из софтфона

**Дата:** 2026-08-03  
**Статус:** утверждён

## Цель

Дать оператору возможность отправить одно SMS только абоненту, с которым он
говорит сейчас или говорил ранее. Оператор выбирает активный SMS-шаблон либо
пишет свободный текст. Номер телефона берётся из звонка и не редактируется.

## Границы

В объём входят:

- отправка из активного звонка;
- отправка из выбранной строки истории звонков;
- выбор активного SMS-шаблона;
- редактирование текста после выбора шаблона;
- полностью свободный текст;
- статусы постановки в очередь и отказа;
- аудит отправителя и привязка к звонку.

В объём не входят:

- рассылки, кампании, сегменты и выбор произвольных получателей;
- ручное редактирование номера;
- планирование отправки;
- просмотр delivery status в софтфоне;
- создание и редактирование шаблонов из софтфона;
- реальная отправка SMS в автоматических тестах.

## Пользовательский сценарий

### Активный звонок

В нижнем ряду действий `ActiveCallView` появляется кнопка «СМС». Она открывает
модальный `SmsComposeDialog`. Перед открытием софтфон получает primary Asterisk
`uniqueId` текущего звонка через существующий `/api/cdr/channel-uniqueid`.

### История звонков

У строки `RecentsView` появляется действие «СМС». Диалог получает UUID выбранной
записи CDR. Номер отображается из этой записи, но не передаётся как доверенный
источник для отправки.

### Диалог

Компактное окно продолжает тёмную визуальную систему существующих диалогов:

1. Нередактируемое поле «Получатель» с номером из звонка.
2. Переключатель «Шаблон» / «Свободный текст».
3. Для шаблона — список активных SMS-шаблонов и поле итогового текста.
4. Для свободного режима — пустое многострочное поле.
5. Счётчик символов. Он информационный и не управляет массовыми сегментами.
6. Кнопки «Отмена» и «Отправить».

После выбора шаблона его `content` копируется в редактор. Оператор может изменить
итоговый текст перед отправкой. Кнопка «Отправить» недоступна при пустом тексте,
невыбранном шаблоне в шаблонном режиме или выполняющемся запросе. Нажатие требует
явного подтверждения с показом номера и финального текста.

Результаты Lazyweb по desktop compose-modal подтверждают простой однооконный
паттерн: адресат сверху, редактор в центре, единственное основное действие снизу.
Отдельный мастер для этой операции не нужен.

## API

### Получение шаблонов

Софтфон использует универсальный существующий endpoint:

```http
GET /api/messages/templates?channel=sms&isActive=true&page=1&limit=100
Authorization: Bearer <JWT>
```

Он уже защищён `message-templates:read`, которое есть у `cc_operator` и
`tm_operator`. SMS-specific controller для чтения не используется, поскольку
он целиком защищён более широким `sms:send`.

### Отправка

Новый endpoint:

```http
POST /api/messages/sms/send-from-call
Authorization: Bearer <JWT>
Content-Type: application/json

{
  "requestId": "uuid",
  "source": {
    "type": "active",
    "id": "asterisk-primary-unique-id"
  },
  "content": "Финальный текст, подтверждённый оператором",
  "templateId": "uuid-or-null"
}
```

`requestId` генерируется софтфоном один раз на попытку и используется как ID
создаваемой `SmsMessage`. Повтор того же запроса возвращает исходный результат и
не создаёт вторую отправку.

Ответ после подтверждённой публикации RabbitMQ:

```json
{
  "id": "uuid",
  "status": "queued",
  "phoneNumber": "+992..."
}
```

Для истории `source` имеет вид `{ "type": "history", "id": "cdr-uuid" }`.
API никогда не принимает номер телефона от клиента. Для активного звонка сервер
проверяет, что ARI-канал аутентифицированного SIP-оператора имеет переданный
primary `uniqueId`, и извлекает внешний номер из каналов этого звонка. Для
истории сервер загружает CDR по UUID, проверяет tenant и принадлежность текущему
оператору теми же полями `agent/channel/accountcode/src/dst`, которые использует
история звонков, и выводит удалённую сторону из CDR/CallSummary. Если источник
не относится к оператору или номер отсутствует, запрос отклоняется до создания
`SmsMessage`.

## Backend flow

Новый `SmsComposeController` делегирует в `SmsComposeService`:

1. Проверить `requestId`, `source`, длину и непустой `content`.
2. Получить организацию и идентификатор оператора из текущего пользователя.
3. Разрешить `source` через отдельный `CallRecipientResolver`: active — через
   ARI и primary `uniqueId`, history — через org/own-scoped CDR UUID.
4. Нормализовать номер существующей телефонной утилитой.
5. Если передан `templateId`, проверить, что шаблон принадлежит организации,
   активен и поддерживает канал SMS. Текст повторно не рендерить: API сохраняет
   именно подтверждённый оператором итоговый `content`.
6. Отклонить отправку для blacklist/DNC-контакта, найденного по нормализованному
   номеру в пределах организации.
7. Создать `SmsMessage` со статусом `PENDING`, направлением `OUTBOUND`, ID равным
   `requestId`, `templateId`, `phoneNumber`, `content`, `organizationId`,
   audit metadata (`createdByUserId`, `operatorId`, `sourceType`,
   `sourceId`, `callUniqueId`) и ссылками на доступные `lead/contact` данные.
8. Опубликовать существующее `sms_send` задание через текущий queue producer.
9. Если публикация не удалась, перевести строку в `FAILED` и вернуть ошибку.

Отправка не использует синхронный `SmsProviderService.sendSms()` из controller и
не создаёт фиктивную кампанию. Реальная доставка остаётся в
`SmsQueueConsumer`, где уже действуют retries и защита от повторной доставки
после принятия провайдером.

## RBAC

Добавляется узкое право `sms:send:own-call`. Оно разрешает только endpoint
`send-from-call` и выдаётся ролям:

- `admin`, `owner`;
- `cc_manager`, `cc_operator`;
- `tm_manager`, `tm_operator`.

Существующее `sms:send` не выдаётся операторам, потому что сейчас оно также
разрешает управление SMS-шаблонами и кампаниями. Создание, изменение и удаление
шаблонов остаётся за существующими управленческими правами.

## Softphone components

- `Models/SmsModels.cs` — DTO шаблона, paginated response, send request/result.
- `Services/SmsService.cs` — Bearer-authenticated загрузка шаблонов и отправка.
- `Views/SmsComposeDialog.axaml` — разметка диалога.
- `Views/SmsComposeDialog.axaml.cs` — состояние, выбор шаблона, валидация,
  подтверждение и вызов сервиса.
- `Views/ActiveCallView.*` — кнопка и получение основного Asterisk `linkedid` для текущего звонка.
- `Views/RecentsView.*` — действие для выбранной записи истории.
- `Assets/i18n/{ru,kk,tg,uz}.json` — подписи и сообщения ошибок.

Сервис следует текущему паттерну `LeadService`/`TaskService`: `BackendUrl`,
Bearer `AccessToken`, `HttpErrorNotifier`, отсутствие отключения TLS-проверки в
новом коде. Диалог не хранит токен и не знает деталей очереди.

## Ошибки и состояния

- Ошибка загрузки шаблонов показывает retry и не запрещает свободный текст.
- `403` показывает отсутствие права отправки.
- `404` означает, что звонок не найден или недоступен текущему оператору.
- повторный `requestId` возвращает существующий результат как успех,
  если сообщение уже `PENDING/QUEUED/SENT`; `FAILED` требует новую попытку с новым
  `requestId` и повторного подтверждения.
- Blacklist/DNC отображается отдельным понятным отказом без постановки в очередь.
- После успешного ответа диалог закрывается и показывает «СМС поставлено в
  очередь». Это не заявляет, что сообщение доставлено.

## Тестирование

### Backend

- controller защищён `sms:send:own-call`;
- номер из body игнорировать невозможно, потому что такого поля нет в DTO;
- чужая организация и чужой оператор получают отказ;
- активный SMS-шаблон принимается, чужой/неактивный/не-SMS отклоняется;
- blacklist/DNC блокирует создание и publish;
- свободный текст создаёт `SmsMessage` без `templateId`;
- шаблонный текст сохраняет `templateId` и подтверждённый `content`;
- повторный `requestId` не публикует второе задание;
- ошибка RabbitMQ переводит запись в `FAILED`;
- миграция/RBAC catalog выдают право только перечисленным ролям.

Тесты queue producer используют mock RabbitMQ и никогда не вызывают реального
SMS-провайдера.

### Softphone

- DTO корректно читают paginated template response;
- выбор шаблона копирует content в редактор;
- переключение на свободный текст не меняет номер;
- пустой текст блокирует отправку;
- повторный клик во время запроса не создаёт второй request;
- запрос содержит `requestId`, `source`, `content`, `templateId`, но не номер;
- активный звонок передаёт primary `uniqueId`, история — UUID CDR;
- HTTP failure оставляет диалог открытым и позволяет повторить с новым
  подтверждением.

## Приёмка

1. Обычный `cc_operator`/`tm_operator` открывает SMS из активного звонка и из
   истории, но не может изменить номер.
2. Можно выбрать активный шаблон, изменить итоговый текст и поставить одно SMS в
   очередь.
3. Можно отправить свободный непустой текст.
4. Нельзя отправить SMS по чужому звонку, на blacklist/DNC или повторно тем же
   `requestId`.
5. Оператор не получает управление шаблонами, кампаниями или сегментами.
6. Автотесты и ручной smoke не доставляют реальное SMS.
